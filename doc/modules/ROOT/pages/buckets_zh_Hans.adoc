= 哈希表基础

容器由多个 _桶_ 组成，每个桶可容纳任意数量的元素。例如，下图展示了一个包含 7 个桶的 `xref:reference/unordered_set.adoc#unordered_set[boost::unordered_set]`，其中容纳了 5 个元素 `A`、`B`、`C`、`D` 和 `E`（仅为示意图，实际容器通常具有更多桶）。

image::buckets.png[]

为确定元素应放入哪个桶，容器首先对元素的键应用哈希函数 `Hash`（对于集合，键即元素本身，但为统一术语，集合和映射均使用“键”这一称谓）。该函数返回 `std::size_t` 类型的值。由于 `std::size_t` 的取值范围远大于桶的数量，容器会对此值进行二次转换以选定目标桶。

检索指定键的元素过程如下：对键执行相同处理以定位目标桶，随后在桶内通过相等谓词 `Pred` 将键与元素逐一比较以匹配结果。若哈希函数设计得当，元素将均匀分布于各桶中，此时仅需检查少量元素即可完成检索。

更多关于哈希函数与相等谓词的信息请参阅下一节的 xref:hash_equality.adoc#hash_equality[相关说明]。

图中可见 `A` 与 `D` 被置于同一桶内。在此桶中查找元素时最多需进行 2 次比较，导致搜索效率降低。此现象称为 *碰撞*。为维持高效性，我们需尽可能减少碰撞发生。

若使用 `xref:reference/unordered_flat_set.adoc[boost::unordered_flat_set]` 替代 `boost::unordered_set`，示意图将呈现如下形态：

image::buckets-oa.png[]

在开地址容器中，每个桶最多容纳一个元素；若发生碰撞（如示例中的 `D`），元素将使用原始位置附近的其他可用桶。基于此简化机制，Boost.Unordered 开地址容器仅提供极其有限的桶访问 API。

== 桶数量控制

随着无序关联容器中元素增加，碰撞概率上升将导致性能下降。为此，容器在插入元素时会自动增加桶数量。用户也可通过调用 `rehash` 主动调整桶数量（如有必要）。

标准虽未强制规定桶数量的确定方式，但基于容器的 _负载因子_（元素总数除以桶数量）提出了若干要求。容器需维持 _最大负载因子_，并确保实际负载因子低于该阈值。

用户无法直接控制桶数量，但可通过两种方式间接影响：

* 在构造容器或调用 `rehash` 时指定最小桶数量。
* 通过 `max_load_factor` 建议最大负载因子。

`max_load_factor` 并非由用户直接设定最大负载因子，而仅提供 _提示_。即使如此，标准也未强制要求容器严格遵循此值。唯一强制要求负载因子低于最大值的场景是在调用 `rehash` 后。但多数实现会尝试将元素数量控制在最大负载因子之下，并将最大负载因子设定为与提示值相同或接近——除非提示值严重偏离合理范围。

关于开地址与并发容器的 `max_load` 说明：在 `rehash` 后或容器创建时，最大负载为 (`max_load_factor() * bucket_count()`)，但在高负载情况下删除元素时该值可能轻微下降。例如，若某 `xref:reference/unordered_flat_map.adoc#unordered_flat_map[boost::unordered_flat_map]` 的 `size()` 接近 `max_load()` 时删除 1,000 个元素，`max_load()` 可能减少约数十个元素。此行为由 Boost.Unordered 内部实现以维持性能稳定，在规划免重哈希插入操作时需予以考虑。
