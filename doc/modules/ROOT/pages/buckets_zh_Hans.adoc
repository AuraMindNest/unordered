== 哈希表基础

[[content]]
[[preamble]]
容器由多个__桶__组成，每个桶可容纳任意数量的元素。例如，下图展示了一个包含7个桶和5个元素（`A`、`B`、`C`、`D`和`E`）的link:reference/unordered_set.html#unordered_set[`boost::unordered_set`]（此图仅为示意，实际容器通常包含更多桶）。

image:buckets.png[桶]

为确定元素应放入哪个桶，容器对元素的键应用哈希函数`Hash`（对于集合，键即元素本身；统一称为键以便集合和映射使用相同术语）。该函数返回`std::size_t`类型的值。由于`std::size_t`的取值范围远大于桶的数量，容器会对此值进行二次转换以选择目标桶。

检索指定键的元素过程如下：对键应用相同流程定位目标桶，随后在桶内通过相等谓词`Pred`比较键与元素以查找匹配项。若哈希函数设计良好，元素将均匀分布于各桶中，只需检查少量元素即可完成检索。

link:hash_equality.html#hash_equality[下一节将提供关于哈希函数与相等谓词的更多信息]。

图中可见`A`和`D`被置于同一桶内。在此桶中查找元素时需进行最多2次比较，导致搜索效率降低。此现象称为**冲突**。为保持高效性，我们需尽量减少冲突发生。

若使用link:reference/unordered_flat_set.html[`boost::unordered_flat_set`]替代`boost::unordered_set`，图示将变为：

image:buckets-oa.png[桶（开放寻址）]

在开放寻址容器中，每个桶最多容纳一个元素；若发生冲突（如示例中的`D`），元素将使用原始位置附近的其他可用桶。基于此简化设计，Boost.Unordered开放寻址容器仅提供极其有限的桶访问API。

[[buckets_controlling_the_number_of_buckets]]
== 桶数量控制

随着无序关联容器元素增加，冲突将增多并导致性能下降。为此容器会在插入时增加桶数量。用户也可通过调用`rehash`主动调整桶数量（如需要）。

标准允许实现者自由选择桶数量确定方式，但需满足基于容器__负载因子__（元素数量除以桶数量）的要求。容器还应维持__最大负载因子__，并努力使负载因子低于该值。

用户无法直接控制桶数量，但可通过两种方式影响：

* {empty}1. 在构造容器或调用`rehash`时指定最小桶数量。
* {empty}2. 通过`max_load_factor`建议最大负载因子。

`max_load_factor`并非由用户直接设置最大负载因子，仅提供__提示__。即使如此，标准也未强制容器严格遵循此值。唯一要求负载因子必须低于最大值的情况发生在调用`rehash`后。但多数实现会尝试将元素数量控制在最大负载因子以下，并将最大负载因子设置为与提示值相同或接近——除非提示值严重偏离合理范围。

|调整桶数量使其至少为`n`，并确保负载因子低于最大值。

|*仅限开放寻址与并发容器* |

|*方法* |*描述*

关于开放寻址与并发容器的`max_load`说明：在`rehash`或容器创建后，最大负载值应为`max_load_factor() * bucket_count()`；但在高负载情况下删除元素时，该值可能轻微下降。例如，若link:reference/unordered_flat_map.html#unordered_flat_map[`boost::unordered_flat_map`]的`size()`接近`max_load()`时删除1,000个元素，`max_load()`可能减少约数十个元素。此机制由Boost.Unordered内部实现以维持性能稳定，在规划免重哈希插入时需予以考虑。
