== 闭址式容器

++++
<style>
  .imageblock > .title {
    text-align: inherit;
  }
</style>
++++

Boost.Unordered 拥有最快的闭址式（通常称为 https://en.wikipedia.org/wiki/Hash_table#Separate_chaining[分离链接法]）实现之一。下图展示了该数据结构的示例：

[#img-bucket-groups, .text-center]
.简单的桶组方法
image::bucket-groups.png[align=center]

系统会分配一个“桶”数组，每个桶依次指向其自身的链表。这使得满足桶迭代的标准要求变得简单直接。遗憾的是，使用这种布局时整个容器的迭代通常很慢，因为必须检查每个桶是否被占用，导致时间复杂度为 `O(bucket_count() + size())`，而标准要求的时间复杂度应为 `O(size())`。

经典的标准实现最终会如下图所示：

[.text-center]
.经典标准方法
image::singly-linked.png[align=center,link=_images/singly-linked.png,window=_blank]

值得注意的是，此方法仅被 pass:[libc++] 和 pass:[libstdc++] 使用；MSVC Dinkumware 实现使用了不同的方法。关于标准容器的更详细分析可参考 http://bannalia.blogspot.com/2013/10/implementation-of-c-unordered.html[此处]。

选择这种特殊布局的数据结构是为了通过将所有节点互连成单向链表来实现整个容器的高效迭代。您可能还会注意到，桶指向桶元素起始位置之前的节点。这样做是为了在不引入双向链表的情况下高效地从列表中删除元素。遗憾的是，这种数据结构引入了额外的间接访问开销。例如，要访问桶的第一个元素，必须执行如下操作：

```c++

auto const idx = get_bucket_idx(hash_function(key));
node* p = buckets[idx]; // 第一次加载
node* n = p->next; // 第二次加载
if (n && is_in_bucket(n, idx)) {
  value_type const& v = *n; // 第三次加载
  // ...
}

```

若采用简单的桶组布局，只需执行以下操作：
```c++

auto const idx = get_bucket_idx(hash_function(key));
node* n = buckets[idx]; // 第一次加载
if (n) {
  value_type const& v = *n; // 第二次加载
  // ...
}

```

实际上，额外的间接访问会对常见操作（如 `insert`、`find` 和 `erase`）产生显著的性能影响。但为了保持容器的快速迭代，Boost.Unordered 引入了一种新颖的数据结构——“桶组”。桶组是桶数组子段的固定宽度视图，它包含一个位掩码（`std::size_t` 类型）用于跟踪桶的占用状态，并包含两个指针以形成非空组的双向链表。示例如下：

[#img-fca-layout]
.Boost 使用的新布局
image::fca.png[align=center]

因此，整个容器的迭代转变为遍历非空桶组（具有常数时间复杂度），从而将时间复杂度降回 `O(size())`。每个桶组仅占用 4 个字的大小，且管理 `sizeof(std::size_t) * CHAR_BIT` 个桶。这意味着在所有常见实现中，桶组引入的每个桶空间开销仅为 4 比特。

关于 Boost.Unordered 闭址式实现的更详细描述，请参阅 https://bannalia.blogspot.com/2022/06/advancing-state-of-art-for.html[外部文章]。有关实现原理的更多信息，请阅读 xref:rationale.adoc#rationale_closed_addressing_containers[对应章节]。

== 开址式容器

该图展示了 `boost::unordered_flat_set`/`unordered_node_set` 和 `boost::unordered_flat_map`/`unordered_node_map` 的基本内部布局。


[#img-foa-layout]
.Boost.Unordered 采用的开址式布局。
image::foa.png[align=center]

与所有开址式容器一样，元素（对于 `boost::unordered_node_set` 和 `boost::unordered_node_map` 则是元素节点的指针）直接存储在桶数组中。该数组在逻辑上被划分为 2^_n_^ 个组，每组包含 15 个元素。除桶数组外，还有一个关联的元数据数组，包含 2^_n_^ 个 16 字节的字。

[#img-foa-metadata]
.元数据字的分解图。
image::foa-metadata.png[align=center]

一个元数据字被划分为 15 个 _h_~_i_~ 字节（每个对应一个关联的桶）和一个溢出字节（图中的 _ofw_）。_h_~_i_~ 的值如下：

  - 0 表示对应的桶为空。
  - 1 表示一种特殊的空桶（称为哨兵桶），用于在容器完全遍历后
  终止迭代。
  - 若桶已被占用，则为从元素哈希值导出的
  简化哈希值。

当查找具有哈希值 _h_ 的元素时，利用 https://en.wikipedia.org/wiki/SSE2[SSE2] 和 https://en.wikipedia.org/wiki/ARM_architecture_family#Advanced_SIMD_(Neon)[Neon] 等 SIMD 技术，可通过少量 CPU 指令快速检查整个元数据字，并在所有 15 个桶中搜索 _h_ 的简化值：不匹配的桶可立即排除，而简化哈希值匹配的桶则需通过与对应元素进行完整比较来检查。若未找到目标元素，则检查溢出字节：

- 若 _h_ mod 8 位置的位为 0，则查找终止（元素不存在）。
- 若该位为 1（表示组已溢出），则使用 https://en.wikipedia.org/wiki/Quadratic_probing[二次探测法]检查后续组，并重复此过程。

插入操作在算法上类似：使用 SIMD 定位空桶，当经过一个满组时，其对应的溢出位被置为 1。

在不支持 SIMD 的架构中，逻辑布局保持不变，但元数据字采用称为位交织的技术编码：这种布局允许我们仅使用标准算术和逻辑运算以相当好的性能模拟 SIMD。

[#img-foa-metadata-interleaving]
.位交织的元数据字。
image::foa-metadata-interleaving.png[align=center]

关于 Boost.Unordered 开址式实现的更详细描述，请参阅 https://bannalia.blogspot.com/2022/11/inside-boostunorderedflatmap.html[外部文章]。有关实现原理的更多信息，请阅读 xref:rationale.adoc#rationale_open_addresing_containers[对应章节]。

== 并发容器

`boost::concurrent_flat_set`/`boost::concurrent_node_set` 和 `boost::concurrent_flat_map`/`boost::concurrent_node_map` 使用上述 xref:structures.adoc#structures_open_addressing_containers[开址式布局]基础，并增加了同步机制。


[#img-cfoa-layout]
.Boost.Unordered 采用的并发开址式布局。
image::cfoa.png[align=center]

采用两级同步机制：

* 容器级：使用读写互斥锁控制任何操作对容器的访问。通常，即使是修改操作，此类访问也处于读取模式（即可并发），因此在大多数实际场景中该级别不存在线程争用。仅当进行重哈希或执行交换、赋值等容器级操作时，访问才处于写入模式（阻塞式）。
* 组级：每个 15 槽组配备一个 8 字节字，其中包含：
  ** 用于同步访问组内任何元素的读写自旋锁。
  ** 一个原子插入计数器，用于如下所述的
  乐观插入。

通过原子操作访问组元数据，查找过程（在组级别）是无锁的，直到需要与先前 SIMD 匹配的元素进行实际比较时，才使用该组的自旋锁。

插入操作采用以下乐观算法：

* 在本地记录探测序列中初始组的插入计数器值（记作 `c0`）。
* 查找过程如上所述。若未找到等效元素，则在探测序列中依次锁定/解锁每个组以搜索可用槽位进行插入。
* 定位到可用槽位后，会抢先占用该槽位（设置其简化哈希值）并原子递增插入计数器：若整个操作期间无其他线程递增该计数器（通过与 `c0` 比较验证），则完成插入；否则回滚并重新开始。

该算法在查找和实际插入阶段争用极低，但代价是若其他线程从同一组开始成功插入导致干扰，则需重新计算。实际测试中重启频率极低，部分基准测试显示仅为百万分之几。

有关实现原理的更多信息，请阅读 xref:rationale.adoc#rationale_concurrent_containers[对应章节]。
