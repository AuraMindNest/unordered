[[rationale_closed_addressing_containers]]
== 闭地址容器

`boost::unordered_[multi]set` 和 `boost::unordered_[multi]map`
遵循无序关联容器的标准要求，因此接口是固定的。但仍需做出若干实现决策，优先考虑标准符合性和可移植性。

http://en.wikipedia.org/wiki/Hash_table[维基百科哈希表条目]对哈希表的通用实现问题进行了全面总结。

[[rationale_data_structure]]
=== 数据结构

通过规定访问容器桶的接口，标准实质上要求哈希表采用闭地址法。

理论上可设计使用其他方法的哈希表。例如采用开地址法，利用查找链模拟桶行为，但存在严重问题：

* 标准要求元素指针不失效，因此元素不能存储在单一数组中，而需间接寻址层——这将丧失开地址法的主要优势：高效性和内存节省。
* 局部迭代器将极度低效，且可能无法满足复杂度要求。
* 迭代器失效的条件限制也构成问题。当冲突率高时开地址法性能急剧下降，而限制条件可能阻碍必要的重新哈希操作。可将最大负载因子设为较低值规避此问题——但标准要求初始值必须为1.0。
* 鉴于标准基于闭地址法设计，若性能表现不符预期将令用户困惑。

因此采用闭地址法。

[[rationale_number_of_buckets]]
=== 桶数量

选择哈希表桶数量有两种主流方法：使用质数数量或2的幂次方数量。

采用质数桶量并对哈希结果取模通常效果良好，缺点是取模运算开销较大。此乃容器既往主要采用的方式。

使用2的幂次方可加速桶选择，但牺牲了哈希值高位比特。对特殊设计的哈希函数仍可取得良好效果，但容器需处理任意哈希函数，故不可依赖此法。

为避免此问题，可对哈希函数应用变换（例见http://web.archive.org/web/20121102023700/http://www.concentric.net/~Ttwang/tech/inthash.htm[Thomas
Wang整数哈希函数文章]）。但此类变换需知晓哈希值比特数，故仅在`size_t`为64位时使用。

自1.79.0版起，改用https://en.wikipedia.org/wiki/Hash_function#Fibonacci_hashing[斐波那契哈希]。此实现通过公式`(h * m) >> (w - k)`确定桶编号：`h`为哈希值，`m`为`2^w`除以黄金分割率，`w`为字长（32或64位），`2^k`为桶数。此法在速度与分布间取得平衡。

自1.80.0版起，结合精密取模运算选用质数桶量，无需1.79.0版所用的用户哈希函数结果"混合"处理。

[[rationale_open_addresing_containers]]
== 开地址容器

C++标准对无序关联容器的规范严格限制了可行实现方案，最重要约束是隐式要求闭地址法。适度放宽此规范可提供充分利用开地址技术的容器变体。

`boost::unordered_flat_set`/`unordered_node_set`及`boost::unordered_flat_map`/`unordered_node_map`的设计遵循Peter
Dimov的https://pdimov.github.io/articles/unordered_dev_plan.html[Boost.Unordered开发计划]。下文讨论核心原则。

[[rationale_hash_function]]
=== 哈希函数

基于丰富功能与跨平台互操作性，`boost::hash`仍是开地址容器的默认哈希函数。但`boost::hash`对整型等基础类型缺乏开地址法所需的统计特性，故实施后混合阶段：

     _a_ ← _h_ *mul* _C_, +
_h_ ← *high*(_a_) *xor* *low*(_a_),

其中**mul**为扩展乘法（64位架构128位，32位环境64位），**high**和**low**分别为扩展字的高/低半部。64位架构中__C__为2^64^∕https://en.wikipedia.org/wiki/Golden_ratio[_φ_]的整数部分；32位中__C__
= 0xE817FB2Du源自https://arxiv.org/abs/2001.05304[Steele与Vigna
(2021)]。

若哈希函数直接适用于开地址法，可通过link:../../../../container_hash/doc/html/hash.html#ref_hash_is_avalanchinghash[`hash_is_avalanching`]特性禁用后混合。`boost::hash`对字符串类型的特化被标记为雪崩式。

[[rationale_platform_interoperability]]
=== 平台互操作性

只要`std::size_t`长度相同且用户提供的哈希函数/相等谓词可互操作，`boost::unordered_flat_set`/`unordered_node_set`及`boost::unordered_flat_map`/`unordered_node_map`的观测行为在不同编译器间确定性一致——包括相同操作序列下元素的完全一致排序。

尽管实现在可用时内部使用https://en.wikipedia.org/wiki/SSE2[SSE2]、https://en.wikipedia.org/wiki/ARM_architecture_family#Advanced_SIMD_(NEON)[Neon]等SIMD技术，但不影响互操作性。例如：带SSE2的x64模式Intel
CPU上Visual Studio的行为，与无SIMD支持的IBM s390x上GCC的行为完全一致。

[[rationale_concurrent_containers]]
== 并发容器

Boost.Unordered开地址容器使用的数据结构亦被选作`boost::concurrent_flat_set`/`boost::concurrent_node_set`及`boost::concurrent_flat_map`/`boost::concurrent_node_map`的基础：

* 开地址法在非并发和并发场景下均优于闭地址方案。
* 开地址布局极适合最小化锁定的并发访问与修改。特别是元数据数组可实现查找操作的免锁设计（直至最终元素比较步骤）。
* 与Boost.Unordered扁平容器的布局兼容性支持link:concurrent.html#concurrent_interoperability_with_non_concurrent_containers[快速转移]所有元素至并发容器（或反向操作）。

[[rationale_hash_function_and_platform_interoperability]]
=== 哈希函数与平台互操作性

在link:#rationale_hash_function[哈希函数默认设置]和link:#rationale_platform_interoperability[平台互操作性]方面，并发容器采用与Boost.Unordered开地址容器相同的决策并提供同等保证。
